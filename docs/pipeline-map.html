Multi-Agent Pipelines

How a task becomes a pull request

Three phases joined by a work queue. You approve intent and review results; everything between runs unattended, in a container that cannot reach a git host and holds exactly one credential.

  • Agent — an AI call. Judgment, non-deterministic. There are only four in the whole system.
  • Scaffolding — a plain script. Same input, same output, every time. Most of the pipeline.
  • You — a decision only you make. Diamonds are decision points.
  • Data — anything stored: a file, a folder, a database. Cylinders are state, not steps.
  • Beads (bd) — the thick-walled cylinder, and the only database here. The task queue and the project memory are the same one; only the host may write to it.
  • Specialist slot — where a domain agent plugs in. Dashed = not built yet.
  • Container — a disposable sandbox (double-edged box), one task each. One at a time today; the dashed extras arrive with the V2 concurrency knob.
  • Outside your machine — beyond the sandbox wall.
  • Refused — the proxy turns it away. An —✕ arrow means blocked; a dotted arrow means read-only.

Four boxes here replace fourteen below, and the merges are the point. The queue and project memory are one store — the same database, the same sole-writer rule, which is why an agent's insight and an agent's task travel the same path home. The runner is one script that claims the task, prepares the clone, waits, collects, and files the result: it is the only thing in the system touching both sides of the freeze. The workspace folder is the container's disk, which is why commits are on your PC the instant they're written and killing a container never loses work.

Read the band crossings first. Only four kinds of thing cross into the sandbox: a fresh clone, two read-only files, one credential, and requests to three hostnames. Only three kinds come back: commits in a shared folder, a status file, and an exit code. Everything else on this page is arranged so that those lists stay that short.

What the arrows deliberately don't show. There is no arrow from any agent to the queue, none from the container to a git host, and none from the verifier back to anything the agent can reach. Those absences are the design; the diagram is as much a map of what cannot happen as what does.

Where the task states live. The lifecycle — open, in progress, closed, blocked — isn't drawn as its own shape here; it's the two labels on the arrows into the database, written by the host and nobody else. The state machine has its own diagram further down.

Every cylinder on the map, and what it actually is. Only one of them is a database — the rest are files, and that is deliberate: state you can read in a text editor and diff in a commit is state you can audit.

Both are checklists in this repo — ONBOARDING.md and PLANNING.md — so if you wrap either in a slash command of your own, the checklist stays the single source of truth and the wrapper follows it. This repo is itself onboarded as a target (dogfooding), so the pipeline can work through its own backlog.

A brand-new project reaches its first autonomous run in four stages — the first three happen once, ever; the fourth is the rest of the project's life:

  1. Create it — however you scaffold a project. You and Claude discuss the language and main technologies (options and a recommendation, your call), the project's rules file is written, and a plain-English spec is approved before anything is built. An existing project skips this.
  2. Write the design doc — for anything big enough to decompose into a backlog: intent, architecture, decisions and why, changed only through its change log. Small projects live on the scaffold's spec alone.
  3. Onboard it — the ONBOARDING.md checklist: GitHub remote, integration branch recorded, frozen-test home, config, image, task database, container-aware instructions. Like wiring a house — done once.
  4. Plan and run, forever — every future feature is a PLANNING.md session and an autonomous run. Never a re-onboarding; the one time the plumbing is touched again is a new dependency, baked into the image during that planning session.

scaffold — create a project interactive · once, at the start

  1. What do you want to build? — described in plain English.
  2. Spec approved first — a "what it should do" list and a concrete "done means" checklist, agreed before anything is built.
  3. Language & main technologies discussed — options with tradeoffs and a recommendation; the developer decides. Small tooling choices stay Claude's.
  4. Project written — the rules file (loaded in every future session), spec, README, starter code.
  5. Git initialized, dependencies installed, and the approved spec built out.
  6. Offers pipeline onboarding — "will the pipeline work on this?" folds the next step into the same sitting.

onboard — make it a target interactive · once per project, ever

  1. GitHub remote verified or created; the project's real integration branch recorded, never assumed; line-ending rules added.
  2. Frozen-test home — tests/acceptance/ created with the freeze rules stated.
  3. Pipeline config written — how to run this project's tests, its branch, its frozen paths, its declared dependencies.
  4. Sandbox image built — a thin Docker layer on the pinned base, holding exactly the declared dependencies.
  5. Task database initialized — the durable queue the runner drains.
  6. Project rules rewritten for containers — an agent waking up inside a sandbox learns where it is and what it must never touch; format hooks removed (they fight the closed network).
  7. Sanity pass — everything committed and pushed, image present, queue answering. The checklist lives in ONBOARDING.md; any wrapper follows it, so there is one source of truth.

Both setup steps are interactive — you and Claude together, which is why they wear the same indigo as your decision points. Nothing in setup runs unattended.

"Spec approved first" means Claude drafts, the human approves. From your plain-English description, Claude writes a "what it should do" list and a "done means" checklist of concrete, checkable outcomes ("saving a game and reloading keeps it" — never "works well"). You edit it until it matches what you want; nothing is built before your yes, because a misunderstanding costs one sentence to fix at the draft and an evening to fix in code. The approved spec is saved into the project and later work is reviewed against it.

The same habit scales up. The scaffold's spec is the lightweight form — a checklist a human verifies by hand. The pipeline's planning session is the industrial form of the identical moment: Claude drafts, the developer approves intent, and the checklist becomes frozen tests a script verifies automatically. Moving a project onto the pipeline upgrades the spec, not the way of thinking.

After onboarding, every visit starts at PLANNING.md: specs drafted, tests frozen, your approval — then the runner takes over and the rest of this page applies.

The approval moment is more than a yes. You read the plain-English "Done means" list and the task's difficulty label (change the label if you disagree — it sizes the critics), and you set the priority order the runner will follow. A developer who wants to can also open the actual test files before they freeze — the prose criteria are the required gate for everyone; reading the tests is optional, offered but never insisted on.

The runner is a plain script on your PC — not an AI. It starts containers, watches clocks, and can kill anything it started.

Ready means a task is open, unclaimed, and everything it depends on is finished. The runner works through them highest priority first, oldest first within a tie, one at a time.

A sandbox is a throwaway computer inside your PC. Each task gets a brand new one with a fresh download of your code, and it is destroyed when the task ends — so nothing leaks between tasks and killing one is always safe.

“Critics attack each spec” is one box above and the section below — it is where most of a bad task gets caught, and the only place the cost of a misunderstanding is still one sentence.

Planning Inside “critics attack each spec”

A critic is one Claude review with no memory of the conversation that produced the spec — a subagent or a fresh session, handed three things: the draft, read access to the repository, and a charter pasted verbatim from advisors/. The blank context is the whole point. A reviewer who watched the spec get written agrees with it; a stranger has to guess at exactly what the coding agent, sealed in a container weeks later, will have to guess at — except the agent guesses silently and ships.

ambiguity

Where would two competent engineers, working from this spec alone and unable to ask a question, build different things?

  • Unpinned outputs — “writes a summary” leaves the where, the what and the shape all open.
  • Terms that shift meaning — one word used for the host .run/ in one line and the container's in another.
  • Quantities left to taste — limits, timeouts, retries: either a number or an explicit “implementer's call”.
  • Silent conflicts — a constraint that contradicts a criterion. Report it; don't pick a winner.
  • Load-bearing adjectives — “robust”, “sensible”, “properly”: each is a decision the spec declined to make.

testability

Which criteria can a script not verify — and which could it verify wrongly? Both end as a green run that proves nothing.

  • Overfitted gates — would this test pass on an implementation that is obviously wrong? Say how, concretely.
  • Self-nesting test runners — the real shadow-01 defect: a test that shells out to the same runner it's running under.
  • Environment inheritance — which inherited variable makes this pass on your PC and fail in the container?
  • Non-determinism — clocks, random ids, ordering. A flaky test is worse than none: it destroys the retry loop's steering signal.
  • Coverage both ways — a criterion with no test, or a test with no criterion, is a spec bug.

scope

Is this secretly several tasks — or a fragment that can't stand alone? One spec = one run = one PR a human reviews in a few minutes.

  • The conjunction test — two clauses joined by “and” touching different layers are usually two tasks.
  • Blast radius — a change spanning separately-built components hides which half broke.
  • Too small to stand — a schema field nothing writes; absorb its consumer or sequence it explicitly.
  • Undeclared dependencies — anything missing gets discovered in a container that cannot install or invent it.
  • Label fit — does the difficulty label match what the review actually found?

Every critic answers in the same four-field object — the same shape a run-time advisor writes into the status file, so a lens can move between planning and run time without being rewritten: 

{
  "advisor": "testability",
  "verdict": "concerns",
  "summary": "A1 forces a self-nesting test runner and A3 rests on human judgment.",
  "details": [
    "A1 'the project's test suite passes' will be checked by running node --test from
     inside node --test. NODE_TEST_CONTEXT is inherited by the child, which reports as
     a nested subtest and fails regardless of the code. Assert on the script's exit
     code instead, or spawn the child with that variable stripped.",
    "A3 'the report reads clearly' is not machine-checkable. Restate as the fields the
     report must contain and their order, or drop it to a review note."
  ]
}

Three verdicts exist and only three. ok — reviewed through this lens, nothing worth acting on. concerns — findings that deserve a decision. error — the review could not be performed, which is a finding about the review, not about the work.

Worked example One session's back-and-forth

The 2026-07-25 session put four specs through the panel — this project's own backlog, planned by the pipeline for the pipeline. Three findings and what they changed. Draft and frozen wording are verbatim; the findings are summarised from that session's critic passes.

Draft

A3 — “advisors/testability.md mentions the nested-test-runner failure mode: contains (case-insensitive) nest and the literal NODE_TEST_CONTEXT.”

testability

An overfitted gate — it passes on an implementation that is obviously wrong. The substring nest occurs in any file that happens to say “nested”; a charter that never explains the failure mode would go green. Name the strings that only a correct charter contains.

Frozen as

A3 requires the literal NODE_TEST_CONTEXT, and a match for nested test or self-nest, and one for environment inherit. The neighbouring criteria hardened with it: “mentions the headings” became line-anchored regexes (^## Lens\s*$), and “each fenced json block” became exactly one fence.

Draft

Task C, labelled hard — “(1) In: the runner exports the project's memories to .run/memory.md … (2) Out: after container exit, the runner files each note via bd remember.”

scope

The conjunction test: two deliverables, one running before launch in workspace prep and one after exit in the publish path. They pass and fail independently and produce a diff a reviewer has to read twice. Split, in dependency order.

Frozen as

Two tasks, both medium: C — memory export at workspace prep, plus the PIPELINE_BD_CMD test seam. D — memoryNotes → bd remember after exit, declared as depending on C. Two PRs, each reviewable on its own.

Draft

Constraint — “if the project has no memories, write the file with a ‘no memories’ line rather than omitting it (stable contract for the container side).”

ambiguity

Unpinned output. The file's path is pinned; its contents are not. One engineer writes # No memories, another (none) — and “stable contract” is exactly the claim that then fails. Nor does the spec say what happens when bd itself errors. Pin the bytes, and pin the error case.

Frozen as

“First line is exactly # Project memory, followed by one line per memory of the form - <key>: <text>. With zero memories or on any bd error, the file's content is the single line (no memories recorded).” The export never throws and always writes the file.

The pattern in all three: a critic never says the spec is bad. It names the exact phrase, says what two different things could be built from it, and stops. Claude revises, you approve the revision — the finding itself decides nothing, which is why a critic can be wrong without costing anything.

Why they are advisory by design. An AI reviewer that could fail a task would void the three-attempt cap and produce overnight failures nobody can act on. The frozen tests are the only authority on pass/fail; a charter that asks its critic to block anything is a bug in the charter.

Findings want to become tests. A lens that keeps flagging the same thing should stop being a review and start being a check — a tolerance, a grep, a dimensional analysis. A test steers the container's retry loop; a review does not. That migration, judgment moving leftward into frozen tests, is the direction the whole registry is meant to travel.

Today this is a human-driven session following PLANNING.md, with three general-purpose charters. The dashed slot is where a domain critic plugs in — the same file format, named in a config rather than wired into the runner. V2 packages the session itself as a skill.

How a container is born. The runner launches each task with a single docker run that hands in everything the task will ever have: the fresh clone of the code (read-write), the pipeline's own scripts — entrypoint and verifier — mounted read-only, the task file and memory file as read-only exports, and environment variables: the task's id, the Claude subscription token, and the proxy settings that force all traffic through the allowlist. The token arrives at launch, is never baked into the image, and is the only credential inside.

Who talks to Claude: the entrypoint, never the runner. The entrypoint script — plain scaffolding, unchangeable from inside — composes the coding prompt from the task file, invokes headless Claude Code, runs the verifier, feeds each failure back as the next attempt's prompt, and calls Claude once more to write the docs summary. Phase order is script logic, not an AI decision. The split is deliberate: the process holding the credential never prompts the model, and the process prompting the model cannot alter what judges it.

Queue How a task moves through the list

Nothing is ever deleted. A task is claimed, then closed or blocked, and every run appends to its notes — so a stuck task reaches you carrying its own history. The host is the only writer. The container has no queue access at all; it reports outcomes purely through its exit code and status file. If it wrote to the queue, those writes would land on a task branch that might never merge, and the work list would fork along with the code.

Memory What the pipeline remembers between tasks

Insights outlive the disposable containers. The memory store is the same database as the task list, and the same rule applies: the host holds the only pen. Agents propose memories through the status file; the runner files them after the container exits. Going the other way, the runner exports current memories to a read-only file at container launch — so each task starts knowing what earlier tasks learned.

Isolation Where the walls are

The container is disposable and nearly powerless: no git credentials, no package registries, no route to the internet except three named Anthropic hosts through a proxy. Work flows one way — your PC hands in a fresh copy of the code, and the container's commits land in a folder shared with your PC, so killing it never loses anything. A solid arrow is an allowed path, an ✕ arrowhead is a refusal, and a dotted arrow is read-only.

What comes back out, and who touches it. The container's entire disk is a folder on your PC, so the code — every commit — is already on the host the moment it's written; nothing has to cross the network to escape the sandbox. After the container exits, plain scripts take over: the runner pushes the branch, assembles the pull request from the spec, the change summary, and the verifier's evidence file, and generates the run report from the manifest. No AI writes the PR or the report. The only AI-written prose in a PR is the change summary the docs phase wrote inside the container — the host pastes it verbatim, never parses it, and never asks a model anything on the way out.

Review When the run finishes

The run report arrives ordered by how much scrutiny each task needs — tampered > stuck > partial > failed > done with retries > done first try — so the top of the report is where your attention goes first. Each kind asks something different of you:

Tampered wants suspicion: something changed a frozen file, and the pushed WIP branch is the evidence. Stuck wants a decision — every allowed attempt failed (three by default, tunable per run), so the spec is probably wrong: fix it and re-approve, amend the design, or drop the task. Partial wants its regression evidence read: the new work passed but something existing broke, and the flagged PR says what. Done wants an ordinary code review — the PR carries the spec, the change summary, and the verification evidence, so judging it needs no archaeology.

"Send back" is not an edit. Feedback on a PR becomes a new task through the normal planning session — nothing is fixed by hand on a pipeline branch, so every change that reaches the integration branch went through the same gates.

Merging is one PR at a time, in your order. Every task forked from the same starting point, so the first merge is clean. If a later PR collides with one already merged, GitHub blocks it with a conflict — and the fix is never a hand-edit: it goes back through planning as a new task that starts from the updated main. The subtler case — two changes that merge cleanly but disagree in behavior — is why overlapping tasks don't share a parallel batch, and why the full sweep after merging a batch is a named step rather than optional hygiene: scripts/test-all.sh runs every suite in sequence, and it is what caught a suite that passed inside the container and failed on the host.

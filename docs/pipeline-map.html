Multi-Agent Pipelines

How a task becomes a pull request

Three phases joined by a work queue. You approve intent and review results; everything between runs unattended, in a container that cannot reach a git host and holds exactly one credential.

built and running today specialist slot — where a domain agent plugs in Slots 1 and 2 need no pipeline code; slot 3 is the one still to build. None of them can fail a task.

Phase 1–3 End to end

Planning is always interactive. Implementation is always autonomous. Nothing during a run can change what “done” means — the tests are frozen before the code exists.

The runner is a plain script on your PC — not an AI. It starts containers, watches clocks, and can kill anything it started.

Ready means a task is open, unclaimed, and everything it depends on is finished. The runner works through them highest priority first, oldest first within a tie, one at a time.

A sandbox is a throwaway computer inside your PC. Each task gets a brand new one with a fresh download of your code, and it is destroyed when the task ends — so nothing leaks between tasks and killing one is always safe.

Implementation Inside one task container

The phase order is scaffolding, not a decision the model makes. The verifier is the only authority on whether the work is done — the agent never judges its own output, and it cannot edit the tests or the verifier.

Queue How a task moves through the list

Nothing is ever deleted. A task is claimed, then closed or blocked, and every run appends to its notes — so a stuck task reaches you carrying its own history. The host is the only writer. The container has no queue access at all; it reports outcomes purely through its exit code and status file. If it wrote to the queue, those writes would land on a task branch that might never merge, and the work list would fork along with the code.

stateDiagram-v2
  [*] --> open: planning creates the task
  open --> in_progress: runner claims it
  in_progress --> closed: done or partial
  in_progress --> blocked: stuck · tampered · failed
  in_progress --> in_progress: rate limit — parked, resumed
  blocked --> open: you fix the spec and unblock
  closed --> [*]

Claiming stops double-picking, and it is why a crashed run leaves tasks stranded in progress — the next run sweeps those back to open before starting. Blocking is what ends the loop: without it, a task that cannot pass would be picked up again on every run, forever.

Isolation Where the walls are

The container is disposable and nearly powerless: no git credentials, no package registries, no route to the internet except three named Anthropic hosts through a proxy. Everything durable stays on the host.

Why blocked matters. It is what removes failed work from the ready queue. A stuck task needs a human decision — fix the spec, fix the design, or drop it — so the loop can never pick it up again and spin.
